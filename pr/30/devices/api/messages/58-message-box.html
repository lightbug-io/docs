Message Box keeps up to 1024 bytes of server-managed data cached on the device for a connected application. GET reads the local cache, SUBSCRIBE delivers later cache updates, and SET replaces or clears the cached bytes.

Applies to Viper devices only

Unsupported products

The cached feature requires supporting firmware. Unsupported products return Not Supported (Status header 4, code 7). Independent Transmit Now uploads are documented separately below and do not imply support for the cached feature.

How syncing works

The device reports its cached-message checksum during a tracking session. If a completed session contains a valid report and the server's configured data has a different checksum, the server can send a version 2 SET with the desired bytes. Unconfigured or invalid server data leaves the cache unchanged; an explicitly configured empty payload requests a clear. When the device accepts the SET, it replaces the cache, saves it when persistent storage is enabled, and publishes to current subscribers. GET reads this local cache; subscribing does not itself fetch data from the server. Later tracking-session reports let the server check the reported cache checksum and offer the update again if it still differs. Sending an update or receiving an ACK alone does not confirm that the cache is synchronized.

2026-10 formatCurrent

Complete payload and CRC-16 format. GET and SUBSCRIBE explicitly select wire Message Version 2 with header 22; omitting it selects the legacy format. SET requires 2.

Message LevelHeader 16
uint8optional

Loosely analogous to log levels (trace, debug, info, warning, etc.) in that you must define the lowest level of interest. Message Levels can be used with timeouts on subscriptions - if a message of the requested level is not available within the specified time, the subscription will be abandoned. Currently you may only define one subscription per message type - requesting multiple levels will result in existing subscriptions being modified to the new level. Future iterations will support "Changes Only" and "Critical" and may support multiple concurrent subscriptions with varying levels

  • 1 · Info-Watch: Receive all messages if and when available, without explicitly requesting that the underlying hardware be turned on.
  • 2 · Info-Auto: Receive all messages and explicitly request underlying hardware be activated to provide the requested data where needed
  • 10 · Valid: Activate the relevant hardware but only receive valid data. May be used with subscription timeout feature to request usable data without leaving the hardware on indefinitely
Subscription IDHeader 17
uint8[]optional

ID of the subscription being managed, when multiple subscriptions are being used per message type (advanced usage). If not provided, Subscription ID 0 is assumed (the default subscription). Can be used to uniquely identify subscriptions when multiple subscriptions of the same message type exist. Devices may have default subscriptions, and these will use Subscription ID 0. So SUBSCRIBing without a Subscription ID, or with subscription ID 0 will, create or modify the default subscription. When using with the SUBSCRIBE or UNSUBSCRIBE methods, you should optionally provide a single uint8 value. If messages are sent as part of a non 0 Subscription ID, one or more Subscription IDs will be included in the message header to identify which subscription(s) the message relates to.

UPLOADMessage 58Message Version 2

Tracking-session uploads

A separate device-to-server context, not a GET response or subscription update. Tracking-session messages always use Message Version 2. Field 129 may carry independent Transmit Now upload data, not the cached down-synced payload. Cached-message CRC reporting is Viper-only. Earlier chunked payload and additive-checksum format, retained for existing integrations. GET and SUBSCRIBE use it when header 22 is omitted, zero, malformed-width, or set to 1. Legacy replies and publications omit header 22 and use checksum field 1 plus nonempty chunks 10-14 concatenated in field-ID order. They do not include CRC field 2 or full-payload field 129. No legacy SET is supported.

Format dates and wire selectors

The date labels identify when each documented format was introduced in source, not a firmware release date. The 2026-10 format uses Message Version 2; the earlier 2025-10 format uses Message Version 1. This header-22 selector is separate from protocol version 3. The numeric values remain visible in the request and response header documentation.

Payload CRC and frame CRC are different

The device calculates and stores CRC-16/XMODEM of the cached payload: polynomial 0x1021, initial value 0x0000, no input or output reflection, final XOR 0x0000. The outer message-frame CRC protects the complete frame. The 16-bit payload CRC can collide for different payloads; an accepted SET still applies changed bytes even when their CRC matches the previous CRC.
