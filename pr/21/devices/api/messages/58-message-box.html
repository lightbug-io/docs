58: Message Box ​

Message Box keeps up to 1024 bytes of server-managed data cached on a Viper for a connected application. GET reads the local cache, SUBSCRIBE delivers later cache updates, and SET replaces or clears the cached bytes.

Applies to Viper devices only

Message formatVersion 2Current referenceVersion 1Legacy reference

The current format is documented below. Legacy fields and examples are collapsed in a separate section.

Jump toGETSETSUBSCRIBEUNSUBSCRIBEUPLOADFirst examples ↓

Viper-only feature

The complete cached Message Box feature is available only on Viper devices running supporting firmware. Other products return Not Supported (Status header 4, code 7).

How syncing works

Viper reports its cached-message checksum during a tracking session. If a completed session contains a valid report and the server's configured data has a different checksum, the server can send a version 2 SET with the desired bytes. Unconfigured or invalid server data leaves the cache unchanged; an explicitly configured empty payload requests a clear. When Viper accepts the SET, it replaces the cache, saves it when persistent storage is enabled, and publishes to current subscribers. GET reads this local cache; subscribing does not itself fetch data from the server. Later tracking-session reports let the server check the reported cache checksum and offer the update again if it still differs. Sending an update or receiving an ACK alone does not confirm that the cache is synchronized.

Current and legacy formats

Message Version 2 is the current format; version 1 remains documented for compatibility. This message-format version is separate from protocol version 3. Set Message Version (header 22) to 2 explicitly for current GET and SUBSCRIBE requests; omitting it selects the legacy format. SET requires version 2.

UPLOADMessage 58

Tracking-session uploads

A separate device-to-server context, not a GET response or subscription update. Tracking-session messages always use Message Version 2. Field 129 may carry independent Transmit Now upload data, not the cached down-synced payload. Cached-message CRC reporting is Viper-only. Independent Transmit Now uploads can use MT58 without cached Message Box support; those upload-only messages omit field 2.

Target Viper or Transmit Now upload-enabled firmware

Device upload (MT58)

When Message Box support is enabled, field 2 reports the cached-message CRC, including 0 for an empty cache. Independent upload bytes in field 129 do not form part of that cached-message CRC.

Payload CRC and frame CRC are different

The device calculates and stores CRC-16/XMODEM of the cached payload: polynomial 0x1021, initial value 0x0000, no input or output reflection, final XOR 0x0000. The outer message-frame CRC protects the complete frame. The 16-bit payload CRC can collide for different payloads; an accepted SET still applies changed bytes even when their CRC matches the previous CRC.
